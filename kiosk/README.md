# DisplayOS Android kiosk

This is an original Java Android app for the contract in `../docs/product-contract.md`. It loads the existing product `/screen` renderer. It does not copy wesbos application code. All source edits are under `kiosk/`; backend, recovery and shared documents remain parent-owned.

The APK compiles locally. Debug and Release both build and verify from the current source with a fresh local demonstration signer, and the full 127-check local suite passes. The debug build is installed on the demonstration SM-T580 with a fresh native enrollment and default Home selected (2026-10-17), so owner-visible local-content success, a personal assistant and cold-boot qualification remain pending. The press-and-hold voice path is fixed and live-verified through the upload — microphone grant, native device-command gate and the server's upload accounting all pass a real begin/part/end cycle from the tablet — and the owner's own spoken message and transcript remain the next check. Earlier owner-confirmed connection, PIN and loop-resolution reports describe an earlier build. Six-slot PIN visuals are deferred. See [build evidence](BUILD-EVIDENCE.md) for exact artifact hashes.

## Build on this Windows machine

Run from `E:\GitHub\displayos`:

```powershell
powershell -NoProfile -ExecutionPolicy Bypass -File kiosk/scripts/setup-tools.ps1
powershell -NoProfile -ExecutionPolicy Bypass -File kiosk/scripts/build.ps1
powershell -NoProfile -ExecutionPolicy Bypass -File kiosk/scripts/test.ps1 -Node 'C:\Program Files\nodejs\node.exe'
powershell -NoProfile -ExecutionPolicy Bypass -File kiosk/scripts/verify.ps1
```

The setup uses `%LOCALAPPDATA%\DisplayOSKioskToolchain` by default. It verifies pinned vendor hashes before copying and extracting the downloads into ACL-protected NTFS storage. Metadata and independent SHA-256 hashes are recorded in the private `toolchain.json`. `Get-KioskToolchain` gates builds, tests and installer signing checks on current-user-only ACLs and no reparse points in the executable trees, metadata and SDK classpath. `setup-tools.ps1 -ProjectLocal` can make a research-only shared copy, but signing/provisioning will not execute it. No PATH, system JDK, UAC, purchase or Android Studio installation is involved. The build uses `javac --release 8`, Android `aapt2`, `D8`, `zipalign` and `apksigner` directly. There is no Gradle, npm dependency or npm PATH assumption. Download and use remain subject to the vendor license files in the SDK/JDK archives.

Outputs are `build/debug/displayos-kiosk.apk` and `build/debug/evidence.json`. Evidence binds the APK hash to every app source file and the downloaded archive hashes. `verify.ps1` rejects source additions, deletions or changes after compilation. Builds include timestamps and are not claimed reproducible byte-for-byte.

Current artifacts: debug `12673680...` (installed on the demonstration SM-T580, enrolled) and release `a508f892...` (not installed), both bound to source `2e664071...`. All 127 checks pass; artifact/source verification accepts 24 app files and eight scripts for both configurations with the new protected signer (`CN=DisplayOS Local Demo`). Parent alone installs. See [BUILD-EVIDENCE.md](BUILD-EVIDENCE.md).

The build needs the HTTPS origin of your deployment, set with the `DISPLAYOS_ORIGIN` environment variable or `build.ps1 -Origin 'https://your-service.example'`. Runtime origin changes are refused. Native credentials cannot be sent to localhost, HTTP, alternate ports or arbitrary media URLs.

## Windows signing and preparation boundary

Signing passwords, signing keys, ticket responses and per-unit exports belong in `%LOCALAPPDATA%\DisplayOSKiosk` on an ACL-capable NTFS volume, not E: exFAT. `protect-runtime.ps1` calls native `icacls`, removes inherited access, grants the current user SID, then verifies every access rule. Any other principal, missing enforceable ACL or reparse point gates the operation. It does not treat mode 0600 as privacy on Windows. Administrators and processes running as the same user remain trusted; ACLs do not defend against them.

The test runner accepts the protected runtime on this machine and refuses the shared exFAT workspace. Its shared-workspace negative fixture is specific to this environment. No reusable secrets are printed, embedded in the APK, passed on command lines or written under E:. The service-local demo and cloud runtimes are separate and untouched.

The debug certificate is a local demonstration certificate. For a non-debug build using the same local demonstration signer:

```powershell
powershell -NoProfile -ExecutionPolicy Bypass -File kiosk/scripts/build.ps1 -Configuration Release -SigningStore "$env:LOCALAPPDATA\DisplayOSKiosk\demo-signing.jks"
powershell -NoProfile -ExecutionPolicy Bypass -File kiosk/scripts/verify.ps1 -Configuration Release
```

Release disables the debug preparation receiver and `run-as` access. This command does not approve a commercial signer. A commercial signing store must be supplied privately with its alias and the runtime `signing-password.txt`, using the same password for the signing key and store. Store custody, certificate continuity, app update policy and licensing need owner approval. Never clear app data or replace the signing identity to fix an enrollment failure.

## Native factory interface

Only an installer uses these commands. Family pages never expose keys, files, factory credentials or device IDs.

On an owner-authorized, connected SM-T580 running API 26 or newer, with USB debugging already approved:

```powershell
powershell -NoProfile -ExecutionPolicy Bypass -File kiosk/scripts/provision.ps1 -Action Export -Serial QUALIFIED_SERIAL -Install -Launch
powershell -NoProfile -ExecutionPolicy Bypass -File kiosk/scripts/provision.ps1 -Action Prepare -Serial QUALIFIED_SERIAL -FactorySecretsFile 'C:\protected-runtime\displayos-product-secrets.json'
```

These are installer reference commands. Parent reports using guarded installation/export/preparation; this delegate did not run them on a tablet. `-Install` is explicit and requires model/API checks, the build content hash, successful APK signature verification and exactly one signer whose certificate SHA-256 matches the private keystore certificate exported with protected password-file input. Editable E: APK/evidence files are not signing authority. The installer copies the APK into current-user-only NTFS runtime first, verifies that copy, and passes only that private copy to ADB to prevent a shared-workspace replacement between verification and install. No install occurs otherwise. `-Launch` starts the native installer activity. ADB invokes native processes without visible Windows UI. The script neither discovers random units nor restarts USB, changes firmware, clears data, selects Home or enables device administration. The selected ADB executable and reviewed scripts remain trusted installer inputs; do not run an unreviewed helper or executable writable by an untrusted party. Parent owns ADB archive/provenance verification.

The app creates a unique P-256 key in Android Keystore. It writes its **public** JWK to app-private `files/public-key.json` and nonsensitive status to `files/unit-info.json`. The script exports them through fixed `adb shell run-as` commands. It validates the JWK has no `d`, checks the installed origin, and writes `native-public-key-SERIAL.json` under the protected runtime. No desktop private key is generated or imported.

The automatic Prepare path is headless: it reads `FACTORY_CREDENTIAL` from an ACL-validated JSON file, requests a ticket for the exported native JWK, and sends only `{ticket,deviceId}` over ADB stdin to the fixed app-private `files/preparation.json`. It never prompts for or supplies a PIN. The receiver consumes and deletes that file, signs the ticket with the existing unit Keystore key, enrolls, verifies an authenticated unclaimed poll without a snapshot, stores the bearer encrypted, and reopens the existing activity using `onNewIntent`. The unclaimed screen shows the parent's QR/manual pairing flow. During deliberate physical home confirmation, the customer chooses exactly six numbers for a screen PIN on the tablet, not the laptop or chat. This PIN is separate from the connection code. Existing six-digit or previously saved 8 to 12 digit PINs still verify; preparation never replaces them. Nothing auto-claims a home. Startup deletes an abandoned plaintext preparation file after process death. Tickets are not shell arguments; the factory credential never reaches Android.

PIN omission is allowed only for a fresh local enrollment with a factory device ID and no stored PIN, or a same-ID retry carrying its encrypted fresh/deferred enrollment marker. Already enrolled units, another pending identity, legacy pending enrollment without that marker and existing PIN records are rejected. The receiver accepts exactly two string fields, or those fields plus a valid string `ownerPin` for legacy manual preparation; unknown fields, nulls, coerced values and an explicit empty PIN are rejected. The on-unit manual ticket + PIN dialog remains supported. An existing PIN must verify and is never overwritten by preparation. Normal key recovery preserves it; only a persisted, previously observed owner-authorized reset followed by unclaimed recovery can clear it. Deferred-PIN recovery also checks authenticated unclaimed state before persisting a recovered bearer.

The parent's factory wrapper can either forward the argument array to this script or issue the same request independently:

```text
Input public key file: %LOCALAPPDATA%\DisplayOSKiosk\native-public-key-SERIAL.json
POST /factory/v1/tickets
Authorization: Bearer <credential read from protected storage>
JSON: {serial,hardwareProfile:"samsung-sm-t580-demo",publicKey:<native P-256 JWK>}
Protected response file: {ticket,expiresAt,deviceId}
```

Then invoke `provision.ps1 -Action Prepare -Serial QUALIFIED_SERIAL -TicketFile 'C:\protected-runtime\native-ticket.json'`. The server's key binding is authoritative; a substituted or desktop-key ticket cannot enroll. Request a fresh ticket for the same native public key if the previous ticket expires before enrollment. Never copy a prepared installation to another unit. The pending device ID is encrypted before enrollment, so a lost enrollment response can be recovered after app restart with Keystore proof. Manual activity enrollment without the factory device ID can retry the ticket while valid, but lacks that pending-enrollment recovery fallback.

If a preparation response was lost, run `provision.ps1 -Action Recover -Serial QUALIFIED_SERIAL`. It launches native pending-enrollment recovery and checks the nonsensitive prepared status without issuing another factory ticket. This is not a backend connectivity proof for an already prepared unit. The screen's normal poll handles rejected existing bearers separately. Manual-entry enrollment without a known pending device ID still needs ticket replay while valid.

After debug factory preparation, a same-certificate non-debug upgrade preserves native identity and removes the ADB preparation entry point. This transition and release signing custody have not been tested on hardware. Release-only first-install public-key export through a commercial factory channel is not implemented; use the reviewed debug staging workflow for this prototype, not an invented universal installer.

## What runs on the unit

- `MainActivity` owns the WebView, physical claim approval, PIN controls and visible-screen ACK gate. Renderer navigation is limited to the fixed HTTPS `/screen`; file/content access, popups, downloads, cleartext, cross-origin requests, redirects, service-worker network, Java interfaces, WebView debugging and screen capture are denied.
- Native interception handles exact GET `/device/v1/poll` and `/device/v1/media/{mediaId}`. It ignores renderer headers and adds the encrypted bearer itself. Public `/product/*` assets never receive it. Approved JPEG/PNG photos have byte and decoded-dimension limits.
- Exact GET `/device/v1/local` is a separate ephemeral transport. It requires a recent online owned poll, unchanged native bearer and a server ownership check. Only this route uses a 35-second native read timeout; connect timeout and every other route remain eight seconds. Responses are at most 32 KiB. Validated `available`, `localEnabled`, safe nonnegative `localRevision`, `cityLabel`, weather/nearby rows, exact attribution, empty `thirdPartyAttributions`, live expiry and `ephemeral:true` reach JS. Incoming expiry may exceed local now plus one hour by at most 30 seconds for bounded clock skew; returned expiry is clamped to the earlier of server expiry and local now plus one hour. Already expired data remains denied; server authority is never extended. Weather rows require exact source attribution. Unavailable responses need only flags/revision; optional arrays must be empty. Unknown fields, address/coordinate/key fields, wrong types and markup fail closed. The backend must exclude addresses/secrets from text values. No local response, provider key or address is persisted or acknowledged. Offline requests fail without fallback. A 404 stays a 404 without upstream error contents.
- A bundled first-script adapter wraps the existing renderer's XHR request helper. A narrowly scoped message port carries only pairing, physical confirmation, render ACK and pending erase commands. It cannot sign arbitrary messages, visit URLs, run shell commands or operate Android. See [PROTOCOL.md](PROTOCOL.md) for the native bootstrap caveat.
- `Vault` encrypts credentials, snapshots, public shell cache and approved photo cache using Android Keystore AES-GCM, a fresh nonce, record-name authenticated context and atomic files in no-backup storage. Expiry, clock rollback beyond five minutes, a monotonic deadline, reset and auth denial block private cache fallback. Removed photo references are pruned. Clear/erase preserves the unit identity and configuration, not family cache. Physical flash erasure is not guaranteed.
- Native polling handles owner-authorized erase itself. It hides the renderer, clears private cache, sends erase, persists the rotated credential and returns only an unclaimed response. A lost response is recovered with a service/unit-bound native signature, never a browser key. A persisted content-denial marker prevents known-reset or revoked state from restoring an older offline snapshot.
- Local physical confirmation requires matching words and the existing owner PIN, or deliberate creation of a new PIN for fresh headless enrollment or after owner reset. PINs use salted PBKDF2-SHA256 and persisted retry backoff. There is no remote PIN reset or automatic home claim. PINs are not household accounts.

Home and BOOT_COMPLETED support are present. If this app is already the authorized Android device owner, `KioskAdmin` allowlists only itself for lock task, pins Home and disables lock-task controls on API 28+. No device-owner installation is executed. The PIN menu can leave lock task for Wi-Fi repair or exit. Managed exit clears its persistent Home choice and opens Home settings. Normal unmanaged Home selection, boot/background-start limits, lock-task escape behavior and return from Wi-Fi must be checked on the real unit. An unmanaged app cannot guarantee prevention of Android system escapes. The native system Wi-Fi page is a deliberate owner action, not remote administration.

Immersive-sticky display mode hides status/navigation bars on resume and foreground focus, but does not reapply while a PIN or installer dialog is open. This is presentation, not a managed escape boundary. Android can reveal system controls. Unmanaged Exit does not restore the previous default Home.

The QR claim renderer comes from the parent-owned `/screen` implementation and its pinned QR library. This kiosk adds no QR library. Parent reports the actual WebView 70 QR/native bridge flow worked on an earlier build; the owner reports completing home connection and the six-digit PIN then. The 2026-10-17 fresh enrollment supersedes that earlier claim; the new physical claim awaits the owner. This delegate did not observe a camera scan or claim. The existing manual code and on-unit confirmation flow remain supported. Agent OAuth/PKCE and MCP are backend responsibilities, not credentials held by the kiosk. There is no universal-agent or provider-support claim.

## Validation and gates

See [BUILD-EVIDENCE.md](BUILD-EVIDENCE.md) for the current artifacts, hashes and check evidence. The JVM suite tests the actual protocol, DER-to-raw codec and HTTP transport using synthetic connection mocks. Eleven additional snapshot regressions execute the unmodified Android 8.1 JSONObject implementation against synthetic fixtures. The runner downloads six official AOSP JSON sources into ignored `.tools/android-json`, verifies pinned vendor Git blob hashes before compilation, and adds no APK dependency. Node tests exercise the adapter and inspect static security boundaries. These are not Android instrumentation tests. Windows ACL tests exercise this machine's filesystem boundary. Four installer checks use real APK signature verification, including a valid differently signed APK with a matching editable evidence hash. They invoke no ADB and do not qualify installation.

The subsequent reconnect defect treated an owned `snapshot:null` as content because JSONObject still reports that key as present. One real-object predicate now governs expiry, content removal, ACK eligibility and unclaimed enrollment/recovery checks. Empty owned state has expiry zero, clears old private content without repeated renderer erasure, and cannot be acknowledged. Actual expired content still fails closed; UI erasure is idempotent while cleared. Tests cover 100 repeated null polls, one content-to-null removal, malformed snapshot types and real expiry followed by stable null state. No unit identity or saved PIN is removed. The owner reports that the loop has stopped after final installation; this is not a render-ACK or long-duration stability claim.

Parent's sanitized crash report exposed a separate startup race: an initialization callback read shared `client` after `onNewIntent` cleared it. Initialization now constructs a captured candidate on the command worker and publishes it only on the UI thread after checking a dedicated reload epoch and activity destruction. Stale completions and errors cannot replace a newer candidate or affect a destroyed activity. Five JVM lifecycle tests and a static wiring regression cover this gate. `SnapshotState` is unchanged by the lifecycle fix. Parent reports no new DropBox crash after three rapid starts plus 15 seconds; cold boot and full Android lifecycle coverage remain unproven.

The first reported live defect was a PIN shorter than eight digits against the prior validator. The hotfix accepts exactly six digits for newly chosen screen PINs, keeps malformed input in the same dialog with a numbers/length hint, and immediately rejects the bridge promise on Cancel. Existing wrong-PIN backoff remains. Fresh salt/hash are computed in a candidate configuration and persisted before replacing live configuration; claim expiry and the volatile activity gate are checked again after the KDF and immediately before vault commit. No PIN or exception detail is logged. Cancel, expiry, changed claim, duplicate dialog, pause, reset and stale WebView generation cannot approve a home. Only confirmation gets a 115-second bridge timeout; other requests remain 30 seconds and the queue remains bounded to eight. The dialog allows at most 90 seconds and reserves at least 15 seconds before server expiry. The owner now reports a successful fresh six-digit physical claim. Retry, cancellation, expiry, cooldown and lifecycle edge cases still need hardware verification; success is not inferred from the automated tests.

Local transport tests exercise actual HTTP authentication, 32 KiB bounds, authorization changes, reject sanitization, offline failure, redirects, MIME and route-specific timeouts through synthetic connections. Adapter and native wiring/schema checks are static where Android classes are involved. Android `JSONObject` schema validation, provider response normalization and the live local endpoint have not been executed on a tablet by this delegate. Google account/project/billing/provider setup and backend epoch/location-version checks belong to the parent; this build makes no provider availability claim.

Twelve deterministic LocalContent tests now execute actual Android JSONObject validation on the JVM with injected time and synthetic content. The observed 2.5-second-lag fixture failed before the fix and passes afterward with expiry shortened to local now plus one hour. Exact 30-second skew passes; 30 seconds plus one millisecond, expired data, wrong types and private extra fields fail. Short server expiry is unchanged. Native authentication/revocation guards are unchanged. Parent reports 42 live Google checks and a successful paired browser trial; this is not physical native weather/nearby proof. Parent owns the exact-local 45-second renderer XHR correction. Native read timeout is per read, not an end-to-end deadline; connect time, later reads and the recent-owned-poll gate remain constraints.

Before customer use, prove native enrollment, QR/manual claim, wrong PIN/backoff, two-home denial, native bearer isolation, visible render ACK, Wi-Fi disconnect/reconnect, offline cold start before expiry, deadline/clock rollback, boot/Home, managed escape denial, lost erase response, app process death and non-debug upgrade on an owner-qualified unit. Audit WebView/OS patch support, Keystore backing and media memory use. No hardware readiness is implied by a signed APK.

Parent reports a connected SM-T580 on Android 8.1/API 27, security patch 2020-06-01 and WebView 70.0.3538.110, with `hardwareBacked:false` for native P-256 identity, not the AES vault key. This delegate performed only authorized read-only clock and installed-APK hash checks, no installation or private UI/data access. Use synthetic demo content only. Parent reports native enrollment/QR bridge and the owner reports PIN/home connection and loop resolution.
